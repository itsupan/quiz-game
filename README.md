# quiz-game

SvelteKit + TypeScript on Cloudflare Workers, with a D1 (SQLite) database.

The home page is a hello world that reads rows from D1 through Drizzle, so the whole
chain — schema → migration → binding → query → render — is already wired and tested.

## Stack

| Concern         | Tool                                                        |
| --------------- | ----------------------------------------------------------- |
| Framework       | SvelteKit 2 (Svelte 5 runes) + Vite 8                       |
| Language        | TypeScript 6 (`svelte-check`)                               |
| Formatting      | Prettier + `prettier-plugin-svelte`                         |
| Linting         | ESLint 10 flat config + `typescript-eslint` + svelte plugin |
| Unit/component  | Vitest 4 (`server` node project + `client` browser project) |
| End-to-end      | Playwright                                                  |
| Database        | Cloudflare D1 (SQLite) via Drizzle ORM                      |
| Hosting         | Cloudflare Workers (`@sveltejs/adapter-cloudflare`)         |
| CI/CD           | GitHub Actions → staging & production                       |
| Package manager | pnpm                                                        |

## Getting started

```sh
pnpm install
pnpm db:setup:local   # applies migrations + seed to the local D1 in .wrangler/state
pnpm dev
```

Open <http://localhost:5173>. `pnpm dev` runs your Worker bindings against local D1, so
`platform.env.DB` behaves the same as it does in production.

```

seeds/dev.sql          Idempotent local seed data

  app.d.ts             App.Platform (Cloudflare Env) and App.Locals types

  lib/server/db/

    schema.spec.ts     Unit test (Vitest, node project)
  routes/

    +page.server.ts    Server load using locals.db
```

## Generated files

`worker-configuration.d.ts` (the `Env` type for your bindings) and `.svelte-kit/` are
generated, gitignored, and rebuilt by the `prepare` script on `pnpm install`. `pnpm check`
regenerates the binding types too, so they can never drift from `wrangler.jsonc`. Run
`pnpm gen` yourself after adding a binding if your editor needs it sooner.

## Scripts

| Script                       | Does                                                                  |
| ---------------------------- | --------------------------------------------------------------------- |
| `pnpm dev`                   | Vite dev server with emulated Cloudflare bindings                     |
| `pnpm build`                 | Typecheck bindings and build the Worker into `.svelte-kit/cloudflare` |
| `pnpm preview`               | Serve the built Worker with `wrangler dev` (real workerd)             |
| `pnpm check`                 | `svelte-check` + verify `worker-configuration.d.ts` is current        |
| `pnpm lint` / `pnpm format`  | ESLint / Prettier (`pnpm format:check` for a read-only check)         |
| `pnpm test:unit`             | Vitest (append `--run` for a single pass)                             |
| `pnpm test:e2e`              | Playwright against a real build served by Wrangler                    |
| `pnpm test`                  | Everything                                                            |
| `pnpm db:generate`           | Generate a migration from `schema.ts` (`--name <label>` optional)     |
| `pnpm db:setup:local`        | Apply migrations + seed to local D1                                   |
| `pnpm db:migrate:staging`    | Apply migrations to the staging D1                                    |
| `pnpm db:migrate:production` | Apply migrations to the production D1                                 |
| `pnpm gen`                   | Regenerate `worker-configuration.d.ts` after editing bindings         |

## Changing the database

1. Edit `src/lib/server/db/schema.ts`.
2. `pnpm db:generate --name <what_changed>` — writes `migrations/NNNN_<name>.sql`.
3. Review the generated SQL, then `pnpm db:setup:local`.
4. Commit the schema **and** the migration. CI applies it to staging/production on deploy.

Drizzle only generates SQL here; Wrangler owns applying it, so migration state is tracked
in D1's `d1_migrations` table rather than by Drizzle.

## One-time Cloudflare setup

Deployment is not configured until you do these three things.

**1. Create the two D1 databases** and paste the returned IDs into `wrangler.jsonc`,
replacing `REPLACE_WITH_STAGING_D1_DATABASE_ID` and `REPLACE_WITH_PRODUCTION_D1_DATABASE_ID`:

```sh
pnpm exec wrangler login
pnpm exec wrangler d1 create quiz-game-staging
pnpm exec wrangler d1 create quiz-game-prod
```

The top-level `database_id` in `wrangler.jsonc` is a placeholder on purpose — local D1
lives in `.wrangler/state` and never uses it.

**2. Add GitHub repository secrets** (Settings → Secrets and variables → Actions):

| Secret                  | Where to get it                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------------ |
| `CLOUDFLARE_API_TOKEN`  | Cloudflare dashboard → My Profile → API Tokens → _Edit Cloudflare Workers_ template, with D1 edit permission |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare dashboard → Workers & Pages → Account ID                                                          |

If you create GitHub Environments named `staging` and `production`, the secrets can live
there instead and you can gate production behind a required reviewer.

**3. Push.** See below.

## CI/CD

`.github/workflows/cicd.yml`:

- **Every push and PR** to `development` or `main` runs: format check → lint → typecheck →
  unit/component tests → build → end-to-end tests.
- **Push to `development`** → after CI passes, applies migrations to the staging D1 and
  deploys the `quiz-game-staging` Worker.
- **Push to `main`** → after CI passes, applies migrations to the production D1 and deploys
  the `quiz-game` Worker.

Migrations run _before_ the Worker is deployed, so the new code never meets an old schema.

Deploy manually with `pnpm deploy:staging` / `pnpm deploy:production` if you need to.
